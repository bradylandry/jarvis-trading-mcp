## Medium

### get_fit_score implementation diverges from tool description
- **File**: `friend_mcp/server.py:175-183`
- **Issue**: The tool is described as returning a "Directional fit score (0-10) with per-component evidence (sentiment, fundamentals, Kimi earnings, Kimi-vs-analyst delta, insider activity)." The implementation calls `/api/screener?tickers=X`, not a dedicated fit-score endpoint. If the screener response format differs from what the tool description implies, Claude will receive misleading context and may misinterpret the result. The comment acknowledges no direct endpoint exists, but the tool description is not updated to reflect the actual screener payload shape.
- **Fix**: Either update the tool description to precisely match what the `/api/screener` endpoint returns (field names, structure), or add a dedicated API endpoint that returns the documented 0-10 score + per-component breakdown. At minimum, confirm empirically that `_api_get("/api/screener", {"tickers": ticker})` returns the fields described in the tool's `description` string.

### TOOLS and TOOL_FNS must be kept in sync manually
- **File**: `friend_mcp/server.py:228,301`
- **Issue**: The `TOOLS` list (the MCP schema declarations that Claude sees) and the `TOOL_FNS` dict (the actual Python callables) are separate data structures with no structural link. There is no assertion, test, or code-level enforcement that every entry in `TOOLS` has a corresponding key in `TOOL_FNS`. A future contributor adding a tool to one but not the other would cause a silent runtime failure (`"Unknown tool"` error returned to Claude on tool call). Currently `get_iv` is present in both (line 210, line 309), but this is only by convention.
- **Fix**: Add a startup-time assertion (or a unit test) that validates `set(t["name"] for t in TOOLS) == set(TOOL_FNS.keys())`. Example: `assert set(t["name"] for t in TOOLS) == set(TOOL_FNS), "TOOLS and TOOL_FNS are out of sync"` in `main()` or at module level.

## Low

### No test suite
- **File**: `friend_mcp/server.py` (entire file)
- **Issue**: The package has no tests. The MCP protocol handler (`_handle`), the rate limiter (`_rate_limit_check`), and all tool functions are untested. `_handle` in particular has multiple branches (initialize, notifications/initialized, tools/list, tools/call, unknown method) that could silently regress.
- **Fix**: Add a `tests/` directory with at minimum: (1) unit tests for `_handle` with mocked `_api_get`, covering each JSON-RPC method; (2) a test that the TOOLS/TOOL_FNS sync assertion holds; (3) a test for `_rate_limit_check` sliding-window behavior.

### Loose dependency pin
- **File**: `pyproject.toml:8`
- **Issue**: `requests>=2.28` is not pinned to an exact version. For a package that friends are instructed to `pip install --upgrade`, a loose pin means any future `requests` minor or patch release is pulled automatically. Given that this package is audit-reviewed before being shared, exact pins (`requests==2.32.3`) ensure the reviewed code is what friends actually run.
- **Fix**: Pin to the specific version in use: `requests==<version>`. Re-pin and note in the changelog on each intentional upgrade.
