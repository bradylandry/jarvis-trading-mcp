## Medium

### `get_fit_score` ignores the `opt_type` parameter
- **File**: `friend_mcp/server.py:183`
- **Issue**: The function signature accepts `opt_type: str = "call"` but the actual API call never passes it — it always hits `/api/screener` with only `{"tickers": ticker.upper()}`. So `get_fit_score("AAPL", "put")` returns identical data to `get_fit_score("AAPL", "call")`. The tool description promises "directional fit score" but direction is silently dropped, which misleads users making trading decisions.
- **Fix**: Either pass `opt_type` to the screener endpoint (e.g., `{"tickers": ticker.upper(), "type": opt_type}`), or — if the screener genuinely doesn't support direction filtering — update the function comment and tool description to say "direction-agnostic", and remove the `opt_type` parameter to avoid false impressions.

## Low

### Unguarded `int()` cast of env var silently kills MCP at startup
- **File**: `friend_mcp/server.py:68`
- **Issue**: `RATE_LIMIT_MAX_CALLS = int(os.environ.get("JARVIS_TRADING_MAX_CALLS_PER_MIN", "30"))` is evaluated at module import time. If `JARVIS_TRADING_MAX_CALLS_PER_MIN` is set to a non-numeric value (e.g., `"120 calls"` or a copy-paste typo), Python raises `ValueError` before `main()` runs. The MCP server exits silently — Claude Desktop / Claude Code shows a generic "server failed to start" error with no useful message.
- **Fix**: Wrap with a try/except and fall back to the default:
  ```python
  try:
      RATE_LIMIT_MAX_CALLS = int(os.environ.get("JARVIS_TRADING_MAX_CALLS_PER_MIN", "30"))
  except ValueError:
      RATE_LIMIT_MAX_CALLS = 30
  ```

### Catch-all exception exposes internal error details to Claude context
- **File**: `friend_mcp/server.py:148`
- **Issue**: `except Exception as e: return {"error": f"{type(e).__name__}: {e}"}` leaks the exception class and message into Claude's context. For `requests` errors this is usually benign (e.g., `"ConnectionError: ..."`) but if the exception carries stack-trace fragments, internal paths, or environment-specific data, they end up in Claude's tool-result and potentially in session logs.
- **Fix**: Either return a generic `{"error": "Unexpected error contacting the API. Contact Brady."}` or log the detail to stderr and return the sanitized message — consistent with the approach already used for non-200 HTTP status codes earlier in the same function.
