## High

### `get_fit_score` silently ignores `opt_type` — bullish and bearish queries are identical

- **File**: `friend_mcp/server.py:183`
- **Issue**: The function signature accepts `opt_type: str = "call"` and the MCP tool schema exposes it as a named input, but `opt_type` is never passed to the API. Both `get_fit_score(ticker="NVDA", opt_type="call")` and `get_fit_score(ticker="NVDA", opt_type="put")` hit the exact same endpoint with the exact same parameters (`/api/screener?tickers=NVDA`), returning identical results. Claude will describe them as different directional analyses when they are not.
- **Fix**: Pass `opt_type` (or whatever the screener endpoint calls the direction parameter) to `_api_get`. If the `/api/screener` endpoint does not accept a direction, the tool description must be corrected and the parameter removed from the input schema. Leaving an ignored parameter in a tool schema is a silent contract violation:
  ```python
  def get_fit_score(ticker: str, opt_type: str = "call") -> dict:
      return _api_get("/api/screener", {"tickers": ticker.upper(), "type": opt_type})
  ```

## Medium

### `JARVIS_TRADING_API` override accepts non-HTTPS URLs — token sent in cleartext

- **File**: `friend_mcp/server.py:57`
- **Issue**: `API_BASE = os.environ.get("JARVIS_TRADING_API", "https://trading.landrycmd.com").rstrip("/")` accepts any URL scheme. If a user (or a misconfigured env) sets this to `http://...`, the bearer token is sent in cleartext HTTP headers. `requests` will not warn or reject this.
- **Fix**: Add a scheme guard at startup:
  ```python
  if not API_BASE.startswith("https://"):
      sys.stderr.write("JARVIS_TRADING_API must be an https:// URL. Refusing to start.\n")
      sys.exit(1)
  ```

### `RATE_LIMIT_MAX_CALLS_PER_MIN` env var crashes module at import if non-integer

- **File**: `friend_mcp/server.py:68`
- **Issue**: `int(os.environ.get("JARVIS_TRADING_MAX_CALLS_PER_MIN", "30"))` runs at module import time with no exception handling. A typo (e.g. `"120 "` with a trailing space, or `"120/min"`) raises an unhandled `ValueError` that crashes the MCP server process before it can emit a useful error. Claude Desktop will show a generic "server failed to start" message with no actionable detail.
- **Fix**: Wrap in a try/except with a clear stderr message and a safe fallback or clean exit:
  ```python
  try:
      RATE_LIMIT_MAX_CALLS = int(os.environ.get("JARVIS_TRADING_MAX_CALLS_PER_MIN", "30"))
  except ValueError:
      sys.stderr.write(
          "JARVIS_TRADING_MAX_CALLS_PER_MIN must be a plain integer. "
          "Defaulting to 30.\n"
      )
      RATE_LIMIT_MAX_CALLS = 30
  ```

### Exception messages leak internal network details to Claude's context

- **File**: `friend_mcp/server.py:148`
- **Issue**: The bare-except fallback `return {"error": f"{type(e).__name__}: {e}"}` forwards the Python exception string directly into Claude's context. A `requests.exceptions.ConnectionError` typically includes the target URL (including any query parameters) and can include internal hostnames or proxy addresses. This is inconsistent with the deliberate sanitization applied to HTTP error bodies (lines 136–144) that was added specifically to prevent leaking upstream content.
- **Fix**: Apply the same sanitization discipline here. Log the raw exception to stderr for debugging, and return only a minimal, user-actionable string to Claude:
  ```python
  except Exception as e:
      sys.stderr.write(f"[friend_mcp] request error: {type(e).__name__}: {e}\n")
      return {"error": f"Unexpected error calling {path}. Check stderr for details."}
  ```

### `get_fit_score` tool description promises per-component data the endpoint may not deliver

- **File**: `friend_mcp/server.py:258–266`, `friend_mcp/server.py:175–183`
- **Issue**: The tool's `description` in `TOOLS` advertises "Components: sentiment, fundamentals, Kimi earnings, Kimi-vs-analyst disagreement, insider activity." The implementation routes to `/api/screener` — a different endpoint than the component-rich paths used by other tools. The actual response shape from `/api/screener` is not documented in this codebase, so it is unknown whether it returns these components. If it does not, Claude will cite a component breakdown that does not exist.
- **Fix**: Either verify `/api/screener` returns these components and document the mapping, or update the tool description to accurately reflect what the endpoint returns. At minimum add a comment in the function body correlating the endpoint's actual response keys to the described components.

### `__version__` and MCP `serverInfo` version are stale at `"0.1.0"`

- **File**: `friend_mcp/__init__.py:15`, `friend_mcp/server.py:334`
- **Issue**: `pyproject.toml` declares version `0.3.0`, but `__init__.py` exports `__version__ = "0.1.0"` and `server.py` hardcodes `"version": "0.1.0"` in the MCP `initialize` response. Any tool that reads the MCP `serverInfo` or imports `__version__` will see an incorrect version. This makes version debugging and audit tracing harder.
- **Fix**: Derive the version from a single source. The lightweight approach — read it from `pyproject.toml` via `importlib.metadata`:
  ```python
  from importlib.metadata import version, PackageNotFoundError
  try:
      __version__ = version("jarvis-trading-friend-mcp")
  except PackageNotFoundError:
      __version__ = "0.0.0-dev"
  ```
  Then reference `__init__.__version__` in `server.py`'s `initialize` response.

### Malformed JSON-RPC messages are silently discarded — no parse-error response

- **File**: `friend_mcp/server.py:387–389`
- **Issue**: Invalid JSON lines from stdin trigger `continue`, sending no response to the client. MCP JSON-RPC 2.0 specifies that a parse error should return `{"jsonrpc": "2.0", "id": null, "error": {"code": -32700, "message": "Parse error"}}`. Silently dropping means debugging a broken client is harder than necessary.
- **Fix**:
  ```python
  except json.JSONDecodeError:
      _send({"jsonrpc": "2.0", "id": None,
             "error": {"code": -32700, "message": "Parse error"}})
      continue
  ```

### No tests

- **File**: repo root (absent)
- **Issue**: There are no automated tests of any kind. The MCP protocol dispatch (`_handle`), the rate limiter (`_rate_limit_check`), and each tool function are entirely untested. Given the project's purpose (routing financial research queries through a token-authenticated API), a bad argument mapping or protocol regression could silently return wrong data.
- **Fix**: Add at minimum a `tests/test_server.py` with:
  - Unit tests for `_rate_limit_check` (window expiry, limit hit, counter increment).
  - Unit tests for `_handle` covering `initialize`, `tools/list`, `tools/call` (happy path and unknown-tool error), and unknown method.
  - `unittest.mock.patch` on `requests.get` for each tool function to verify the correct endpoint + parameters are assembled (this would have caught the `get_fit_score` opt_type bug above).
