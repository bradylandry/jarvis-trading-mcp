## High

### deploy.sh: re-runs never update the running container app; new ACR accumulates orphans
- **File**: `deploy.sh:16`
- **Issue**: `ACR="acrjarvismcp$RANDOM"` generates a new, unique ACR name on every run. A fresh `az acr create` + `az acr build` push the new image to that new registry. When `az containerapp create` finds the app already exists, it fails and the error is suppressed (`2>/dev/null || echo "app exists; updating below"`). However, there is no subsequent `az containerapp update --image ...` to point the existing app at the new registry or new image. The net result: every re-run after the first builds and pushes to an orphaned ACR that the container app never pulls from. The running app stays on whatever image was deployed the first time. The orphaned ACRs also accumulate costs.
- **Fix**: Either (a) fix `ACR` to a deterministic, stable name (e.g., `ACR="acrjarvismcp"`; ensure global uniqueness via naming convention rather than `$RANDOM`) and add an `az containerapp update -n "$APP" -g "$RG" --image "$ACR.azurecr.io/$APP:latest" -o none` after the failed-create branch, or (b) use `az containerapp up` which handles both create-and-update in one idempotent command.

## Medium

### Backend token cached indefinitely — Key Vault secret rotation silently ignored
- **File**: `friend_mcp/server.py:73`
- **Issue**: `_token_cache` is set once and never cleared. If the Key Vault secret (`JARVIS_TOKEN_SECRET_NAME`) is rotated — a routine security hygiene operation — the server continues forwarding the old, potentially revoked token to the upstream trading API until it is manually restarted. Long-running Container App instances could go for days or weeks using a rotated-away token, causing all tool calls to fail with 401s.
- **Fix**: Store the token alongside a fetch timestamp and re-fetch from Key Vault when the cached value is older than a configurable TTL (e.g., 1 hour). The lock structure already supports this — just add `_token_cache_time: float | None = None` and check `time.monotonic() - _token_cache_time > TOKEN_TTL_S` inside the lock.

### Tool parameters forwarded to upstream API without validation
- **File**: `friend_mcp/server.py:146`
- **Issue**: Parameters such as `opt_type` (accepted as any string, expected "call"/"put"), `mode` (expected "plan_b"/"plan_a"/"directional"), and `dte` (expected positive integer) are forwarded to the upstream API without any validation. The model can pass arbitrary strings that trigger undefined upstream behavior, and any resulting upstream error reveals only the HTTP status code — making debugging harder. For `dte`, `int(dte)` is applied but negative or zero values are not rejected.
- **Fix**: Add explicit allowlist checks at the top of each tool (e.g., `if opt_type not in ("call", "put"): raise ValueError(...)`). FastMCP supports `Literal` type annotations which enforce this automatically: `opt_type: Literal["call", "put"] = "call"`.

### `AUTH_CLIENT_SECRET` not validated at startup; silent auth misconfiguration
- **File**: `friend_mcp/server.py:53`
- **Issue**: `client_secret=os.environ.get("AUTH_CLIENT_SECRET")` passes `None` silently when the env var is absent. If `AzureProvider` requires a client secret for this app registration type and receives `None`, the `FastMCP` instance is created without error but every inbound auth attempt will fail at request time. There is no startup log or guard warning the operator that auth is misconfigured. In a deployed environment this means the server appears healthy but rejects all clients.
- **Fix**: Assert `AUTH_CLIENT_SECRET` is non-empty when `AUTH_CLIENT_ID` is set: `if not os.environ.get("AUTH_CLIENT_SECRET"): raise SystemExit("AUTH_CLIENT_SECRET is required when AUTH_CLIENT_ID is set")`. Add a startup `print`/`logging.info` confirming auth is enabled with which tenant.

### deploy.sh: `az keyvault set-policy --name` receives full URL with trailing slash, not vault name
- **File**: `deploy.sh:52`
- **Issue**: `${KV_URL#https://}` strips only the `https://` scheme prefix, leaving `kv-jarvis-lab2.vault.azure.net/`. The `--name` argument for `az keyvault set-policy` expects only the vault's short name (`kv-jarvis-lab2`). The command always fails silently (`2>/dev/null`), so the Managed Identity never gets the Key Vault `get` permission granted automatically. Every deployment requires a manual RBAC/policy grant as the fallback message notes, but operators may not notice since the script exits 0.
- **Fix**: Use `${KV_URL#https://}` combined with basename extraction: `KV_NAME="${KV_URL#https://}"; KV_NAME="${KV_NAME%%.*}"` to get just `kv-jarvis-lab2`, or switch to RBAC: `az role assignment create --role "Key Vault Secrets User" --assignee "$PID" --scope "$(az keyvault show --name kv-jarvis-lab2 --query id -o tsv)"`.

### No structured logging or audit trail
- **File**: `friend_mcp/server.py:1`
- **Issue**: The server has no logging. Tool invocations, upstream API errors, auth events, and rate-limit hits are invisible beyond what FastMCP may internally emit. For a multi-user server (described as "2-3 trusted friends" with per-user tokens and usage attribution) this makes it impossible to diagnose abuse, attribute costs, or investigate incidents after the fact.
- **Fix**: Add Python `logging` at module level and emit structured log lines at INFO for each tool call (tool name, parameters, response status, latency) and at WARNING for rate-limit hits and upstream non-200 responses. FastMCP may provide middleware hooks; otherwise wrap `_api_get`.

## Low

### `get_fit_score` tool passes `tickers` (plural) param but documents and accepts only one ticker
- **File**: `friend_mcp/server.py:164`
- **Issue**: The underlying API endpoint is `/api/screener?tickers=...` (plural), suggesting it may support comma-separated multi-ticker queries. The tool signature accepts only a single `ticker: str` and the docstring says "for a ticker". If the API supports batching, the tool under-exposes it; if it does not, the param name mismatch is confusing.
- **Fix**: Either rename the API param usage to `ticker` if the upstream truly only supports one, or extend the tool to accept `tickers: str` (comma-separated) to match the upstream API capability.

### `run-local.sh` is macOS-only with no helpful error on other platforms
- **File**: `run-local.sh:7`
- **Issue**: `security find-generic-password` is a macOS Keychain command. On Linux or Windows CI it fails with `security: command not found`, leaving no actionable message. A developer trying to run this on Linux gets a confusing error.
- **Fix**: Add a platform check at the top: `[[ "$(uname)" == "Darwin" ]] || { echo "run-local.sh requires macOS Keychain (security command). On Linux, set JARVIS_TRADING_TOKEN directly." >&2; exit 1; }`.

### `TIMEOUT_S = 90` is very high for an HTTP MCP server under concurrent load
- **File**: `friend_mcp/server.py:45`
- **Issue**: A 90-second upstream timeout means a slow or hung trading API response ties up a server thread for 90 seconds per call. Under concurrent load this can exhaust thread pool capacity. The current use case (few trusted friends) makes this unlikely to matter in practice, but it is an unaddressed scalability risk if use grows.
- **Fix**: Consider a lower default (e.g., 30s) with a `JARVIS_TRADING_TIMEOUT_S` env override, matching the pattern used for `RATE_LIMIT_MAX_CALLS`. Also use `httpx.AsyncClient` with async tools if FastMCP supports it, which eliminates the thread-blocking concern entirely.
