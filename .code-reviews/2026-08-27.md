## High

### `get_fit_score` silently ignores `opt_type`, always calls the screener without it
- **File**: `friend_mcp/server.py:164-167`
- **Issue**: The function accepts `opt_type: str = "call"` and the README shows usage examples like `get_fit_score(ticker=MSTR, opt_type=put)` implying it shapes the result. In practice the parameter is never forwarded — `_api_get("/api/screener", {"tickers": ticker.upper()})` omits it entirely. Every call gets the same neutral screener response regardless of the `opt_type` argument, silently misleading the caller.
- **Fix**: Either forward the parameter — `{"tickers": ticker.upper(), "type": opt_type}` — if the upstream `/api/screener` endpoint supports it, or remove it from the signature and docstring/README to match the actual behaviour.

### `az keyvault set-policy` receives a full hostname instead of a vault name
- **File**: `deploy.sh:52`
- **Issue**: `--name "${KV_URL#https://}"` strips only the scheme. With `KV_URL="https://kv-jarvis-lab2.vault.azure.net/"` the result is `kv-jarvis-lab2.vault.azure.net/`, a full FQDN with a trailing slash. The `az keyvault set-policy` command expects only the short vault name (`kv-jarvis-lab2`). The command will fail, leaving the Managed Identity without the `get` permission it needs on the Key Vault secret, which means the deployed app cannot retrieve the backend token at startup.
- **Fix**: Extract just the vault name: `KV_NAME="${KV_URL#https://}"; KV_NAME="${KV_NAME%%.*}"` (or derive it from a separate variable), then pass `--name "$KV_NAME"`. Alternatively, store the vault name as its own variable rather than deriving it from the URL.

## Medium

### ACR created with `--admin-enabled true`, bypassing managed-identity pull
- **File**: `deploy.sh:29`
- **Issue**: `az acr create ... --admin-enabled true` enables a shared username/password admin credential on the registry. The Container App then authenticates with this credential (`--registry-server`) rather than via its system-assigned Managed Identity. Admin credentials are a single static secret with no rotation, no per-principal audit trail, and broader permissions than a pull-only identity needs.
- **Fix**: Remove `--admin-enabled true`. Assign the `AcrPull` role on the registry to the Container App's Managed Identity (`az role assignment create --role AcrPull ...`) and add `--registry-identity system` (or the MI resource ID) to the `az containerapp create` command. The ACR admin credentials can remain disabled.

### `$RANDOM` in the ACR name makes `deploy.sh` non-idempotent
- **File**: `deploy.sh:16`
- **Issue**: `ACR="acrjarvismcp$RANDOM"` generates a different registry name on every script invocation. Re-running the script (e.g., to update OAuth env vars or roll the image) creates a second ACR and builds a fresh image there, while the existing Container App still points at the original registry. The image update is silently a no-op on the live app unless the operator also manually updates `--registry-server`.
- **Fix**: Use a fixed, deterministic name (e.g., `ACR="acrjarvismcp"` or derive it from `$APP`) so the script is safe to re-run. Add a comment that ACR names must be globally unique and document the one-time-setup vs update-run distinction.

### No input validation on user-supplied tool parameters
- **File**: `friend_mcp/server.py:146-198`
- **Issue**: Tool functions accept `ticker`, `strike`, `expiration`, `opt_type`, `mode`, `budget`, and `dte` directly from the model/caller and forward them as query parameters with no shape or range checks. While httpx URL-encodes them (preventing injection into the request itself), the upstream API sees whatever the caller sends: e.g., a negative `budget`, an `expiration` that is not a valid date, or an `opt_type` outside `call|put`. Errors surface only as opaque `trading API returned status NNN` messages.
- **Fix**: Add lightweight guards at the top of each tool (e.g., `if opt_type not in ("call", "put"): raise ValueError(...)`, `datetime.date.fromisoformat(expiration)` for the expiration field, `budget > 0`, `dte > 0`). These turn silent misbehaviour into clear, early errors and reduce malformed requests reaching the upstream API.

### No tests for any code path
- **File**: `friend_mcp/server.py` (entire file)
- **Issue**: There are no test files anywhere in the repository. The core logic — the rate limiter's sliding-window eviction, the double-checked locking in `_backend_token`, the `main()` fail-closed guard, and each tool's parameter forwarding — has no automated coverage. The `get_fit_score` `opt_type` bug (above) would have been caught by even a minimal integration test that asserts the query params forwarded to the API.
- **Fix**: Add a `tests/` directory with at minimum: a unit test for the rate limiter (inject a full window, assert the exception, advance time, assert recovery), a unit test for the fail-closed guard in `main()` (mock `host` and `_auth`), and a parametrized test for each tool that monkeypatches `_api_get` and asserts the exact query params forwarded. `pytest` + `pytest-mock` are sufficient.

## Low

### `ALLOW_UNAUTHENTICATED=1` escape hatch combined with `HOST=0.0.0.0` default in Dockerfile
- **File**: `friend_mcp/server.py:206-211`, `Dockerfile:6`
- **Issue**: The fail-closed guard correctly refuses to start without auth on a non-loopback bind, but documents `ALLOW_UNAUTHENTICATED=1` as an override. The Dockerfile bakes in `HOST=0.0.0.0`. If a future operator sets only that flag (e.g., during a quick test deployment) and forgets to also set `AUTH_CLIENT_ID`, the server starts with no user authentication listening on all interfaces. The footgun is small but real.
- **Fix**: Consider removing `ALLOW_UNAUTHENTICATED` entirely and requiring either a loopback bind or `AUTH_CLIENT_ID`. If it must exist, rename it to something harder to type casually (e.g., `DANGER_DISABLE_AUTH_FOR_TESTING_ONLY`), add a loud startup warning log, and explicitly exclude it from the documented deployment env vars so it is not seen as a normal configuration knob.

### Missing health/readiness endpoint
- **File**: `friend_mcp/server.py` (no `/health` route defined)
- **Issue**: The Container App has `--min-replicas 1` but there is no `/health` or `/ready` HTTP endpoint. Azure Container Apps (and any load balancer in front) uses HTTP health probes to decide whether to route traffic to the replica. Without a probe, the platform falls back to a TCP check on port 8080, which passes even if the app is initialising or has a stuck backend-token fetch. A failed token fetch would cause every tool call to raise `RuntimeError` while the container reports healthy.
- **Fix**: Register a simple `/health` GET route on the FastMCP/Starlette app (or a sidecar path if FastMCP doesn't expose arbitrary routes) that returns `{"status": "ok"}`. Wire it as the Container App's liveness probe. This also gives operators a cheap sanity check at deploy time.

### `resp.json()` not guarded against malformed upstream responses
- **File**: `friend_mcp/server.py:142`
- **Issue**: If the upstream API returns HTTP 200 with a non-JSON body (e.g., an HTML error page from a proxy, or a truncated response), `resp.json()` raises `json.JSONDecodeError`, which propagates to the caller as an unhandled exception with a Python traceback rather than a clean error message.
- **Fix**: Wrap the call: `try: return resp.json() except Exception: raise RuntimeError("trading API returned a non-JSON response.")` This matches the info-leak-hygiene principle already applied to non-200 status codes.
